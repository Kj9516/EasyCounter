# EasyCounter — техническое задание для Replit

**Версия:** 1.0 — согласованная функциональная основа, с явно отмеченными техническими допущениями  
**Платформы:** iOS и Android  
**Стек:** React Native + Expo, TypeScript  
**Язык интерфейса MVP:** русский (допущение, легко локализовать позднее)  
**Цель документа:** дать Replit Agent однозначный план построения универсального мобильного конструктора счетчиков, не подменяя его набором заранее запрограммированных сценариев.

> **Первое поручение агенту Replit:** до реализации проверить доступность мобильного Expo-workflow и тестирования на физических iOS/Android-устройствах в текущем окружении Replit. Если возможности ограничены, сообщить о них и предложить способ запуска через Expo Go / development build. Не заменять мобильное приложение веб-сайтом без согласования.

## 1. Концепция и жесткие принципы

EasyCounter — локальное мобильное приложение, в котором пользователь создает **проекты** со своими **параметрами, экранами, правилами, виджетами и таймерами**. Пользователь сам определяет значение параметров и поведение приложения с помощью событий, условий, выражений и действий.

**Никакой предметной логики в движке:** он не знает, что такое «игра», «победа», «очки», «кошелек», «игрок» или «здоровье». Такие понятия существуют только в названиях и правилах, созданных пользователем. Пример шахматных часов — лишь тест универсальности, а не встроенный режим.

- Один проект содержит несколько экранов. Все экраны проекта обращаются к общим параметрам и правилам. Разные проекты изолированы.
- Логика «**событие → условие (необязательное) → упорядоченные действия**» универсальна.
- Параметры связываются по внутренним стабильным ID, переименование не разрывает ссылки.
- Все действия одного правила выполняются **последовательно**; каждое следующее видит изменения предыдущих.
- Порожденные события добавляются в очередь и обрабатываются **после завершения текущего правила**.
- Несколько правил, подписанных на одно событие, выполняются **в порядке, заданном пользователем**. Очередь событий — FIFO.
- **Каждое фактическое изменение** параметра порождает отдельное событие, даже если в одном правиле параметр менялся многократно; история old/new сохраняется для каждого события.
- Результат всей цепочки от одного исходного события фиксируется атомарно: успешное окончание → запись; ошибка или отмена → откат.
- Глубокие циклы разрешены, **фиксированного лимита глубины нет**. При подозрении на бесконечное исполнение приостановить и предложить продолжить/отменить/просмотреть источник; по умолчанию не записывать промежуточное состояние.
- Циклы в графе **вычисляемых параметров запрещены**. Это не относится к обычным триггерам.
- Приложение работает локально без обязательной регистрации, сервера и интернета; поддерживает импорт/экспорт.

## 2. Объектная модель

### 2.1. Проект

`id`, `name`, `description?`, `createdAt`, `updatedAt`, `settings`, `screens[]`, `parameters[]`, `rules[]`, `history[]`, `runtimeState`.

Конфигурация проекта (описание элементов, правил, формул) **отделена** от текущего состояния (значения, состояние таймеров, история). Создание копии, общий/выборочный сброс, экспорт шаблона и полного проекта должны опираться на это разделение.

### 2.2. Параметры

Общие поля: `id`, `name`, `type`, `initialValue`, `value` (для обычных параметров), `settings`, `createdAt`.

Типы:

1. `integer` — целое число.
2. `decimal` — точное десятичное число; **десятичная**, а не бинарная арифметика для расчетов; вычислительная точность отдельно от точности отображения.
3. `string` — произвольный текст.
4. `boolean` — логическое значение.
5. `list<T>` — последовательность значений **одного указанного типа**. Для MVP запретить вложенные списки, если это не требуется тестовыми сценариями (техническое допущение).
6. `date` — календарная дата.
7. `time` — время суток.
8. `datetime` — дата и время с ясной политикой часового пояса.
9. `duration` — интервал времени.
10. `timer` — параметр с динамическим отсчетом и командами start/pause/stop/reset; текущая отображаемая величина имеет семантику длительности.

**Вычисляемый параметр** — способ получения значения (формула + результирующий тип), не отдельный примитивный тип. Только для чтения; его результат обновляется **после каждого изменения зависимости** и доступен последующим действиям. При создании/редактировании формулы проверять граф зависимостей и запрещать циклы.

Каждый параметр имеет начальное значение; общий и выборочный сброс возвращают выбранные параметры к начальным значениям с согласованным поведением таймера. Сброс инициируется явным действием пользователя и обрабатывается как операция движка.

### 2.3. Правило

- `id`, `name`, `enabled`, `priority/order`, `eventSource`, `triggerMode`, `condition?`, `actions[]`.
- Триггер поддерживает два режима: **при каждом подходящем событии, если условие истинно**; **при переходе условия false → true**.
- Источники событий: нажатие/другие поддерживаемые взаимодействия виджета; фактическое изменение параметра; явное присваивание значения (отдельно от изменения); достижение порога/окончание таймера; периодический интервал; календарное расписание; открытие проекта (поддерживаемый вид источника).
- Для события изменения хранить snapshot: `sourceId`, `occurredAt`, `oldValue`, `newValue`, тип события. `delta` рассчитывать для совместимых числовых/временных значений. Выражения видят текущие значения параметров **при исполнении**, а контекст события — снимок при возникновении.
- Логические условия: `NOT`, `AND`, `OR`, `==`, `!=`, `>`, `>=`, `<`, `<=`, `contains`, математические и логические выражения; скобки, соблюдение приоритета.
- Выражение условий должно иметь результат `boolean`; преобразования типов только **явными функциями**.
- Внутри правила действия строго упорядочены и могут менять разные параметры.

### 2.4. Действия

Минимальный набор:

- присвоить значение;
- увеличить / уменьшить на указанное значение;
- вычислить выражение и присвоить результат;
- изменить список: добавить, удалить, заменить элемент (валидировать индексы и тип);
- запустить, приостановить, остановить, сбросить таймер;
- запросить ввод во всплывающем окне;
- показать сообщение во всплывающем окне;
- при необходимости вызвать выполнение другого правила через явное событие (не создавать специальную предметную операцию).

Ввод из окна допускается **двумя способами**: во временную переменную текущей цепочки, доступную следующим действиям, либо сразу в выбранный параметр. При отмене ввода отменяется незавершенная цепочка (согласуется с атомарным откатом). Время ожидания пользователя не считается временем вычисления.

Показывать внешние визуальные эффекты (в частности информационные сообщения) только после успешной фиксации, если они не являются необходимым шагом получения входных данных. Не пытаться «откатывать» уже показанные окна.

### 2.5. Время и расписание

- Таймер может отсчитывать вверх либо вниз, хранит стартовое значение и состояние (`running/paused/stopped`); разрешение уходить ниже нуля **настраивается отдельно для каждого таймера**.
- Основа расчета — прошедшее реальное время, а не запись значения в базу каждую секунду. Отрисовка может обновляться часто, но события и сохранение не должны зависеть от FPS.
- Периодическое событие «каждые N единиц времени» не требует пользовательского таймера.
- Календарное расписание: время суток, день недели, дата, повторяемые интервалы; явно учитывать часовой пояс и переходы времени.
- Если приложение закрыто/приостановлено, ОС не гарантирует точного выполнения фоновых задач. При возвращении восстановить расчет и применить политику каждого правила: **все пропущенные / один раз / пропустить**.
- Вариант «все» должен воспроизводить последовательность хронологически. Каждое самостоятельное периодическое срабатывание считать отдельной корневой операцией (техническое уточнение, предварительно рекомендовано, но отдельно не утверждалось).

### 2.6. Экран и виджеты

- Экраны в проекте имеют настраиваемое название, порядок и сетку размещения.
- Визуальный редактор: **сетка с изменяемыми размерами виджетов**, перетаскивание/перестановка, адаптация к разным размерам экранов.
- Два режима: **использование** (запускает пользовательские действия) и **редактирование** (меняет конфигурацию, не запускает действия).
- Минимальные виджеты: кнопка, текст/значение, поле ввода, переключатель, выбор из списка, индикатор, контейнер. Историю можно вывести позднее, поскольку механизм хранения уже есть.
- К любому **подходящему** виджету можно привязать поддерживаемое взаимодействие и правило.
- Внешний вид/доступность/видимость/текст/цвет могут зависеть от универсальных выражений над параметрами.
- Для создания условий и действий предусмотреть **оба способа**: визуальный редактор и текстовые выражения. Оба работают через один безопасный движок, а не через исполняемый JavaScript.

## 3. Формулы, типы, ошибки

- Общий parser/AST/evaluator используется для вычисляемых параметров, условий, действий и динамических свойств интерфейса.
- У типов явные правила совместимости. Примеры: `date + duration`, `duration + duration`, `number + number`; несовместимые операции запрещать при проверке.
- Приведение типов только явными функциями (`Число`, `Текст`, и т.п.). Не делать скрытого сравнения строк по длине: использовать `Длина(строка)`.
- Базовые функции: `min`, `max`, `abs`, `round`, `floor`, `mod`, `length`, `contains`, `if`, функции работы со списками/датами; фактические названия локализовать в редакторе.
- Выражения ссылаются на параметры по ID, но отображают пользовательские названия и поддерживают переименование.
- Отсутствующая ссылка, деление на ноль, недопустимый индекс, несовпадение типов, числовое переполнение, неверная формула → структурированная ошибка с указанием правила и действия; **откат всей корневой цепочки**.
- Предотвращать циклы вычисляемых параметров до сохранения конфигурации.
- При редактировании формулы проверять синтаксис и типы до применения; не оставлять проект в тихо неработоспособном состоянии.

## 4. Движок: контракт выполнения

1. Поступает **корневое событие** (например, нажатие).
2. Создается изолированное временное рабочее состояние проекта; существующее сохраненное состояние остается неизменным до commit.
3. Находятся подходящие правила, выполняются в выбранном порядке; проверяются условия/режим срабатывания.
4. Действия внутри каждого правила выполняются последовательно над рабочим состоянием.
5. Любое фактическое изменение создает **отдельное** событие со снимком `oldValue/newValue`. После каждого изменения актуализируются зависимые вычисляемые параметры; их изменения также должны быть наблюдаемы для универсальных правил (техническое допущение для единообразия).
6. Сгенерированные события попадают в FIFO и обрабатываются после текущего правила. При нескольких подписанных правилах соблюдается настройка порядка.
7. Если очередь пуста и нет ожидаемого ввода, результат атомарно фиксируется: состояние + записи истории. Если ошибка/отмена — рабочее состояние отбрасывается.
8. Циклы в **правилах** разрешены. Использовать раннее обнаружение повторяющихся `(состояние + очередь + позиция исполнения)` где возможно; предохранитель на чрезмерное время/ресурсы **не является жестким лимитом количества шагов**. При подозрении на зацикливание приостановить и показать «Продолжить / Отменить / Подробнее». Нельзя обещать математически точное обнаружение любого бесконечного цикла.
9. Пока ожидается ввод, продолжение цепочки не должно потерять контекст. Для MVP не требовать одновременного исполнения нескольких цепочек над одним проектом — обрабатывать входящие действия последовательно (техническое допущение).
10. При аварийном закрытии приложения безопасно восстановить последнюю **подтвержденную** версию состояния. Поведение незавершенных окон ввода после перезапуска — **не утверждено**; безопасный MVP-вариант: отмена незавершенной операции.

**Тонкость порядка:** если в правиле A меняется 0→5→10, создаются два независимых события 0→5 и 5→10. При их последующей обработке `ТекущееЗначение(A)` может быть уже 10, а `НовоеЗначение` первого события равно 5. Это намеренная семантика.

## 5. Хранение, история, сброс, импорт/экспорт

- Локальное надежное хранилище на устройстве (техническая рекомендация: SQLite через совместимый Expo-модуль; конкретный пакет выбрать по текущей поддержке Replit/Expo).
- **Полная история завершенных операций**, доступная пользователю, с возможностью очистки. В истории хранить исходное событие, время, список изменений параметров, происхождение (виджет/правило), результат. Незавершенную цепочку не добавлять как успешную операцию.
- Опциональная команда отмены последней завершенной операции рассматривается как пользовательская функция, ранее предложена, но отдельно **не утверждалась как обязательная**. Не блокировать MVP ради сложного undo с таймерами.
- Общий и выборочный сброс параметров по `initialValue`.
- Удаление используемого параметра: показать список зависимостей, предложить заменить ссылки/исправить связи/отменить удаление. Не удалять молча.
- Импорт и экспорт файлов через стандартный выбор/поделиться. Минимум два режима: **шаблон** (конфигурация + начальные значения, без текущего состояния и истории) и **полный проект** (конфигурация + состояние, история по выбору).
- Файл должен быть версионирован (`formatVersion`, `appVersion?`, `exportedAt`); при импорте валидировать схему, типы, ссылочную целостность и размер; не выполнять произвольный код из файла; устранять конфликты ID копированием/переназначением в рамках импортируемого проекта.
- Сохранение атомарно, чтобы сбой приложения не оставил проект частично обновленным.
- Облако, аккаунты и многопользовательская синхронизация **не входят в MVP**.

## 6. UX: минимальные основные экраны

1. **Главная:** список проектов, создание, копирование, импорт, экспорт, удаление.
2. **Рабочий экран проекта:** экраны/вкладки, виджеты и их действия, переключатель редактирования.
3. **Редактор экрана:** добавление, перемещение, изменение размера виджетов; настройки внешнего вида, данных, взаимодействий и динамических свойств.
4. **Параметры:** создание/редактирование типов, начальных значений, формул, таймеров, просмотр зависимостей.
5. **Правила:** события, режим срабатывания, условие, порядок действий, порядок правил, включение/отключение.
6. **История и настройки проекта:** просмотр/очистка истории, сброс, импорт/экспорт, часовой пояс и политики расписаний.

Сохранять простой сценарий: новый проект → создать числовой параметр → вывести значение → добавить кнопку `+5` → нажать и увидеть результат. Не заставлять пользователя понимать AST, очередь, транзакции и идентификаторы.

## 7. Этапность работы Replit Agent

### Этап A — базовый мобильный проект
- Создать Expo + React Native + TypeScript проект.
- Проверить запуск на iOS и Android и локальную персистентность.
- Реализовать навигацию: проекты → экраны → настройки проекта.

### Этап B — универсальный движок (прежде сложного UI)
- Реализовать строгие типы, безопасный движок выражений, десятичную арифметику.
- Реализовать операции над параметрами, вычисляемые параметры и проверку циклов формул.
- Реализовать очередь событий FIFO, правила, порядок, snapshots, атомарный commit/rollback, понятные ошибки.
- Добавить автоматические тесты на взаимодействие правил и откат.

### Этап C — минимальный редактор и MVP-сценарии
- Простой список/редактор параметров и правил, поддержка визуального редактора выражений и продвинутого текста.
- Сетка виджетов, привязка данных, действия при нажатии, динамические свойства.
- Окна ввода и сообщения, история, сбросы.

### Этап D — время, импорт/экспорт, отладка
- Таймеры, периодические и календарные события, политика восстановления пропусков.
- Импорт/экспорт; проверка корректности импорта.
- Ручные end-to-end тесты на двух мобильных платформах.

Агенту: **не писать все сразу одним гигантским изменением**. После каждого этапа показывать результат, тесты, известные ограничения и путь запуска на телефоне. Не добавлять предметные сущности даже «для удобства».

## 8. Приемочные тесты (обязательные)

1. **Простой счетчик.** Параметр N=0. Кнопка +5 нажата три раза → N=15. Сброс → N=0.
2. **Конвертация.** Цент=95, Доллар=0. Кнопка +250 центов; универсальное правило `Цент >=100` делает `Доллар += floor(Цент /100)`, `Цент = mod(Цент,100)` → Доллар=3, Цент=45.
3. **Порядок.** Золото=100, Серебро=50; правило из двух действий: удвоить Золото, затем `Серебро = Серебро + (Серебро - Золото)` → Золото=200, Серебро=−100.
4. **События каждого изменения.** A=0; правило A=5, A=10, A=15 → очередь содержит три события с переходами 0→5, 5→10, 10→15; контекст этих событий корректен.
5. **Формулы.** C=A+B; изменение A обновляет C немедленно; попытка создания взаимного цикла вычисляемых параметров блокируется.
6. **Откат.** Правило изменяет A, затем делит на ноль → постоянное значение A и история успешных действий не меняются; пользователь видит причину.
7. **Ввод.** Кнопка открывает окно ввода, значение прибавляется параметру; отмена ввода откатывает предварительные изменения цепочки.
8. **Таймеры.** Два таймера, созданные пользователем кнопки переключают их; при достижении 0 пользовательское правило показывает текстовое сообщение и сбрасывает значения. В движке нет «победы/игры».
9. **Пропущенные интервалы.** При интервале 5 минут и пропуске 20 минут режимы «все/один/пропустить» дают 4/1/0 запусков при корректной границе отсчета.
10. **Защита.** Цепочка A→B→A с конечным условием исполняется; подозрительный бесконечный цикл приостанавливается с возможностью отмены без частичной фиксации.
11. **Экспорт.** Проект экспортируется, импортируется как независимая копия, связи по ID не ломаются; данные других проектов не меняются.
12. **Переименование/удаление.** Переименование параметра сохраняет формулы; при удалении используемого параметра показываются зависимости.

## 9. Открытые технические вопросы, не блокирующие старт

Это **не утвержденные пользовательские решения**. Выбрать простую безопасную реализацию, документировать и при необходимости согласовать:

- Детали автообнаружения циклов; алгоритм приостановки без UI-зависания.
- Правило внешних событий во время ожидания ввода (MVP: очередность, без параллельной записи).
- Точная семантика события «переход условия false→true», когда выражение зависит от нескольких параметров; зафиксировать историю истинности по правилу и повторно оценивать при изменении любой зависимости.
- Генерация `changed` событий при пересчете вычисляемых параметров (по умолчанию — да, при изменении значения).
- Поведение таймеров при настройке отрицательного отсчета, достижении 0, рестарте устройства и перепадах wall clock.
- Безопасные лимиты **ресурсов**, валидация экспорта и максимальная точность decimal (не вводить фиксированный лимит глубины правил).
- Уведомления при закрытом приложении не гарантируются без платформенных механизмов/сервера; не обещать точное расписание в фоне.
- Команда отмены уже завершенного действия (undo) и механика внешнего пользовательского потока отмены — отложить при необходимости.

## 10. Критерии завершенности MVP

- Пользователь без кода может собрать счетчик с несколькими параметрами и зависимыми правилами, расположить виджеты на экране и пользоваться им на телефоне.
- Продвинутый пользователь может вводить выражения текстом; при этом не исполняется произвольный код.
- Поведение цепочек детерминировано, ошибки понятны, данные не теряются и не сохраняются наполовину.
- Работают оба типа событийных триггеров, вычисляемые параметры, таймеры, восстановление периодических событий, история, сброс, импорт/экспорт.
- Все функциональные сценарии описываются универсальными примитивами. **Внутри приложения нет жестко запрограммированной логики игр, счетчиков очков, финансов или иных предметных областей.**
