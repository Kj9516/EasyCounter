# Журнал технических решений

## Этап A

- **Локальная база — SQLite (`expo-sqlite`) с транзакциями.** Выбрана потому, что ТЗ рекомендует SQLite, а приложение должно надежно сохранять проекты без интернета. Для этапа A структура ограничена проектами и пустыми экранами; универсальные параметры и состояние появятся в следующих этапах.
- **Начальный экран проекта пустой и создается автоматически.** Это дает понятный путь «проект → экраны» без заранее встроенной предметной логики.
- **После закрытия приложения восстанавливаются только подтвержденные записи SQLite.** Несохраненное экранное состояние и будущие незавершенные цепочки в этом этапе не сохраняются.
- **Дизайн и интерфейс первого этапа — на русском.** Это следует из допущения MVP в ТЗ; архитектура данных от языка интерфейса не зависит.
- **SQL-операции тестируются тем же репозиторием поверх встроенного SQLite Node.js.** Тестовый адаптер реализует минимальный интерфейс `expo-sqlite` и использует настоящую временную SQLite-базу; отдельная реализация запросов для тестов не дублируется.
  **Почему:** нативный модуль Expo нельзя запустить в обычном Node.js test runner, а дополнительная сторонняя SQLite-зависимость не нужна.
  **Ограничение:** это проверяет реальные SQL-запросы и повторное открытие файла, но не проверяет native bridge `expo-sqlite` на устройстве; физическая проверка остается обязательной.
- **Репозиторий EasyCounter самодостаточен и не зависит от пакетов монорепозитория.** Неиспользуемая ссылка на `@workspace/api-client-react` удалена из приложения и TypeScript project references; нужные внешние версии указаны непосредственно в `package.json`.
  **Почему:** публичный репозиторий содержит только EasyCounter и должен собираться после обычной установки зависимостей без копирования API-клиента и других приложений.
  **Как применять:** новые runtime/dev dependencies добавлять непосредственно в манифест приложения и включать в его lockfile; не полагаться на workspace catalog.

## Этап B — первый пакет движка

- **Движок работает как чистая функция над копией состояния.** Он не записывает данные в SQLite и не вызывает UI; вызывающий код сможет сохранить завершенный результат одной SQLite-транзакцией на следующем шаге интеграции.
  **Почему:** ошибка или отмена корневой операции должны оставлять подтвержденное состояние нетронутым.
- **Длинная цепочка исполнения делится на продолжимые порции.** После ограниченного числа действий `execute` возвращает временный handle с `continue` и `cancel`. Это ограничение одного прохода, а не общий лимит числа действий; результат состояния доступен только после завершения.
  **Почему:** правило циклам разрешено, а принудительный общий лимит противоречил бы ТЗ. Реализация пока дает API для паузы/отмены, но интерфейс этапа C еще не подключен.
- **Точная decimal арифметика ограничена 1000 цифрами и 1000 знаками после запятой.** Деление по умолчанию округляет до 18 знаков, половины округляются от нуля.
  **Почему:** сохраняем точную десятичную арифметику и ограничиваем рост BigInt из формул. Превышение границ возвращает ошибку и откатывает всю временную цепочку.
- **Проверка движка использует текущий Node test runner и тот же TypeScript output, что SQLite-тесты.** Отдельные зависимости для движка не добавляются.
  **Ограничение:** эти тесты проверяют чистую логику в Node, но не интеграцию с Hermes, экраном приложения или SQLite commit.
